How to read this document

This guide draws on two categories of information, and they carry different confidence levels. Keep the distinction in mind, especially if you are using this for vendor due diligence.

Linx does not publish public technical documentation. Compliance artifacts (SOC 2, HIPAA) are gated behind their trust center at trust.linx.security. Everything marked Protocol below is derived from the published APIs of Okta, Microsoft, Google, Ping, and others, which admit only a small number of legitimate authorization paths. Where Linx has a choice among those paths, this guide flags the choice rather than assuming one.

01

Platform overview

Linx Security is an identity security, governance, and administration platform (IGA plus ISPM) founded in 2023, headquartered in New York, and funded through a $50M Series B led by Insight Partners in March 2026. Named customers include Wiz, Aramark, Peloton, Discount Tire, Allegro Microsystems, New American Funding, Evolv, SmartCentres, and Achieve.

VendorThe platform covers five functional areas:

  1. Modern IGA. Access requests, approvals, provisioning, and automated user access reviews across SaaS, cloud, and on-premises.
  2. Identity Security Posture Management. Continuous mapping of identities, entitlements, and resources to surface dormant accounts, admin sprawl, SSO bypass, and missing MFA.
  3. Just-in-Time access. Time-bound, right-sized grants replacing standing privilege, with AI risk scoring on each request.
  4. Identity lifecycle management. Automated joiner, mover, leaver flows with role-based and attribute-based enforcement.
  5. Non-human and agentic identity governance. Service accounts, API keys, bots, and AI agents in the same graph as humans, each tied to an owner and purpose.

VendorThe delivery model is multi-tenant SaaS at app.linxsecurity.io, transactable through the AWS and Azure marketplaces. The integration model is agentless: no migration, no parallel infrastructure, and no long implementation before value.

Network implications

ProtocolBecause all connectors are outbound API clients, the customer opens no inbound firewall rules and deploys no software for cloud-hosted targets. Two exceptions require attention:

  • Webhook and event delivery. If Linx subscribes to Okta event hooks or Microsoft Graph change notifications, the IdP delivers events inbound to a Linx-hosted endpoint. That endpoint is on the Linx side, so the customer still opens nothing, but the customer's IdP is now making outbound calls to a vendor URL, which some egress policies restrict.
  • On-premises targets. Anything not reachable from the public internet (Active Directory, PingFederate, legacy LDAP, on-prem ERP) cannot be reached by a purely outbound SaaS connector. See section 4.5.

Data handling questions to resolve

OpenConfirm before contract:

  • Data residency and region pinning for the tenant.
  • Per-tenant key isolation for signing keys, refresh tokens, and API credentials, versus a shared vault with logical separation.
  • Retention period for ingested audit and sign-in logs.
  • Whether identity attributes are pseudonymized at rest.
  • Sub-processor list, particularly for the AI inference layer, and whether customer identity data is used in any model training.

03

Pre-integration checklist

Gather before the first connector is configured.

Access and approvals

  • Named owner for each target system, with authority to grant tenant-wide consent
  • Change advisory approval for the IdP consent grant, which is tenant-wide and not reversible per-object
  • Decision on read-only pilot versus read plus write from day one (see 9.4)
  • Security review of the vendor's egress endpoints and IP ranges for allowlisting

Environment inventory

  • Primary IdP and any secondary or legacy IdPs still issuing tokens
  • Authoritative HR system and its worker population, including contingent workers
  • Application inventory with owner, criticality, and provisioning method
  • Cloud accounts, subscriptions, and projects in scope
  • Known non-human identity population: service accounts, API keys, CI/CD tokens, bots

Correlation readiness

  • A stable join key present in both HR and the IdP (employee ID is strongest, email is weakest)
  • Documented naming conventions for service accounts and shared accounts
  • List of exception accounts that must never be auto-remediated (break-glass, vendor support, legacy service identities)

Scale note. One Achieve customer described integrating 314+ applications. Plan the application phase as an ongoing program, not a one-time cutover.

Phase 1: Identity provider connectors

This is the foundational connector. Everything else correlates against it.

4.1 Okta

ProtocolPath A, scoped OAuth (preferred). An OIDC service application with private_key_jwt client authentication. Linx holds an RSA private key and publishes the public key as a JWKS. Each token request signs a client assertion.

POST https://{yourOrg}.okta.com/oauth2/v1/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=okta.users.read okta.groups.read okta.apps.read
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion={signed_JWT}
{
  "token_type": "Bearer",
  "expires_in": 3600,
  "access_token": "eyJ...",
  "scope": "okta.users.read okta.groups.read okta.apps.read"
}

Path B, SSWS API token (legacy). A static token bound to a service account, sent as Authorization: SSWS {token}. It inherits that account's admin role rather than a scope list. Two operational hazards: Okta API tokens are revoked after 30 days of inactivity, and tokens issued by a deactivated user are rejected outright, so the service account must be excluded from your own offboarding automation.

OpenAsk Linx which path their Okta connector uses. Scoped OAuth is the correct answer. If the answer is SSWS, ask whether the token can be bound to a custom admin role with a restricted resource set rather than a super admin.

ProtocolPagination. Cursor-based via the Link header with rel="next". Maximum 200 records per page. No offset parameter, no total count.

Rate limiting. Per-org and per-endpoint. Responses carry X-Rate-Limit-Limit, X-Rate-Limit-Remaining, and X-Rate-Limit-Reset. On exhaustion Okta returns 429. A well-built connector reads the remaining header and paces itself rather than waiting for the 429. Ask what percentage of your org's budget a full sync consumes, because a governance vendor competing with your own automations for the same budget causes production incidents.

Change detection. Okta has no delta query. Either poll GET /api/v1/logs?since={cursor}, where latency equals the poll interval, or use event hooks. Event hooks require a one-time verification handshake: Okta sends a GET with an X-Okta-Verification-Challenge header, and the endpoint must echo the value back before Okta will deliver events.

Three credential types, in ascending order of security: client secret (a shared password, avoid), certificate assertion, and workload identity federation (Linx presents a token from its own IdP, no secret or certificate ever exchanged).

ProtocolDelta query. Entra is the only major IdP with a first-class incremental primitive. GET /v1.0/users/delta returns changed objects plus an opaque @odata.deltaLink. Replay that link on the next run to receive only what changed, including deletions as @removed annotations. This is why an Entra-primary environment syncs far more cheaply than an Okta-primary one.

Batching. POST /v1.0/$batch accepts up to 20 sub-requests, materially reducing round trips on per-user fan-out. Pagination is @odata.nextLink, opaque, followed until absent. Throttling is 429 with Retry-After, applied per-app per-tenant, so a badly paced vendor sync degrades your other Graph consumers.

Change notifications. POST /v1.0/subscriptions with a notificationUrl, clientState, and expirationDateTime. Microsoft validates the endpoint by sending a validationToken that must be echoed within 10 seconds. Subscriptions have a maximum lifetime, roughly 3 days for directory resources, and must be renewed. Ask how renewal failure is detected and alerted.

4.3 Google Workspace

ProtocolDomain-wide delegation. In Admin Console under Security, Access and data control, API controls, Domain-wide delegation, authorize the vendor's OAuth client ID against an explicit scope list. The service account then impersonates an administrator.

POST https://oauth2.googleapis.com/token

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion={signed_JWT}

Where the JWT contains iss (service account), sub (the impersonated admin's email), scope, and aud.

The structural weakness. There is no way to scope domain-wide delegation below "acts as the impersonated administrator." The scope list is the only control surface. Grant the minimum, review it periodically, and treat the delegation entry itself as a privileged object in your own posture management.

The tokens endpoint deserves attention. It enumerates every third-party OAuth grant a user has issued, which is the single richest source for shadow SaaS discovery in a Google environment. MFA state comes from the isEnrolledIn2Sv and isEnforcedIn2Sv fields on the user object. Pagination is pageToken and nextPageToken. Change detection is weaker than the other two: most implementations poll the Reports API.

4.4 Secondary identity providers

ProtocolPingOne. A worker application using client credentials against https://auth.pingone.com/{envId}/as/token, with the "Identity Data Read Only" role. Read endpoints sit under https://api.pingone.com/v1/environments/{envId}/ for users, groups, populations, applications, roleAssignments, and activities.

PingFederate. Administrative API at /pf-admin-api/v1/, typically on-premises. Treat as an on-prem target.

JumpCloud. Static API key in an x-api-key header. Read /api/systemusers, /api/v2/usergroups, /api/v2/applications, and Directory Insights for events. A static unscoped key is a weaker credential model than either Okta or Entra offer.

4.5 On-premises Active Directory

OpenThis is the most important open question in the integration. "Agentless" and "on-premises directory support" are in tension. A purely outbound SaaS connector cannot reach a domain controller. Three plausible resolutions, with very different security implications:

  1. Read AD indirectly through Entra Connect. Hybrid-joined objects synced to Entra carry onPremisesSamAccountName, onPremisesDistinguishedName, onPremisesSyncEnabled, and onPremisesImmutableId. Useful AD visibility with zero on-prem footprint, but only for synced objects. Unsynced OUs, disabled-but-present accounts, and AD-only service accounts stay invisible, and those are exactly where offboarding gaps hide.
  2. A customer-hosted collector or relay. Something runs inside the network, reads over LDAPS or Kerberos, and pushes outbound. Works fully, but the agentless claim carries an asterisk. Ask about the runtime, the patching model, the credential it uses, and whether it can run read-only.
  3. A cloud-hosted connector over private link or VPN. Rare, high friction.

Ask which applies, and specifically whether AD-only accounts with no Entra representation appear in the graph. If they do not, partial-offboarding detection has a blind spot in precisely the system most likely to retain stale access.

VendorJoiner, mover, and leaver workflows execute automatically when events trigger them. That requires an authoritative worker record upstream of the IdP.

SystemAuthorizationNotes

Integration design points

  • Effective dating. HR systems carry future-dated hires and terminations. A connector reading only current state will fire leaver automation late. Confirm that Linx reads effective dates, not just current status.
  • Contingent workers. Contractors often live in a different Workday population or outside HR entirely. Decide their authoritative source explicitly, because they are statistically the largest source of orphaned accounts.
  • Termination signal latency. The gap between an HR termination write and the leaver workflow firing is your exposure window. If the HR connector polls nightly, that window is up to 24 hours regardless of how fast the remediation engine is.

6.3 Non-human identity discovery

ProtocolThe discovery sources that actually produce an NHI inventory:

  • Entra: servicePrincipals, applications with credential expiry, managed identities
  • Okta: /api/v1/apiTokens, service-type app integrations
  • Google: tokens per user, service accounts in the linked GCP org
  • AWS: IAM users with access keys, roles with trust policies, key age from the credential report

Ownership assignment is the hard part, and it is a data quality exercise rather than a technical one. Budget for it.

Identity correlation and the graph

VendorData is modeled across human, non-human, and agentic identities to reveal access and risk relationships, surfacing dormant accounts, admin sprawl, SSO bypass, and missing MFA.

Linx's own product material illustrates the output well: one person resolved across an Okta account carrying an admin role, an Entra account, an Active Directory account, and a GitHub account tagged "local." That local tag denotes an account existing outside SSO, and it is the SSO-bypass finding. It only exists because the correlation step stitched four directories together first.

Join keys, strongest to weakest

  1. employeeId present in both HR and IdP
  2. onPremisesImmutableId or sourceAnchor for hybrid AD
  3. onPremisesSamAccountName
  4. userPrincipalName
  5. Primary email
  6. Normalized display name plus manager chain (fuzzy, last resort)

If your environment lacks a stable ID in the IdP, fixing that before deployment will do more for output quality than any platform tuning.

Derived findings and their inputs

FindingRequires
Partially offboarded userHR termination state plus every downstream account
SSO bypassApp-level local accounts plus IdP app assignment
Missing MFAFactor enrollment plus policy scope, not just policy existence
Dormant accountLast-login from the log source, not the user object
Admin sprawlRole assignments plus role privilege, plus PIM eligibility
Orphaned NHICredential inventory plus last-use plus an owner field

Note the pattern. Most useful findings require two or three connectors, not one. A single-IdP pilot will underrepresent the platform's output.

9.3 Just-in-Time access

VendorStanding privileges are replaced with time-bound, right-sized grants, with AI evaluating each request for risk and recommending approve or deny.

ProtocolTwo implementation models, and the difference matters. Native time-bound means Entra PIM eligibility schedules expire in the platform of record: if Linx is unavailable at expiry, the grant still lapses. Scheduled revocation means Linx grants access then calls back later to remove it: if Linx is unavailable at expiry, the grant persists. Ask which model applies per target system. Scheduled revocation converts a vendor availability problem into a standing-privilege problem.

9.4 The read-to-write consent gap

Plan for this explicitly. The write permissions above are a materially different consent grant than the read permissions in section 4. User.ReadWrite.All and okta.users.manage are not what a security team approves for a read-only pilot. A discovery pilot on read scopes is low friction and demonstrates value quickly, but moving to remediation requires a second consent conversation with whoever owns the tenant, and in a regulated environment that is a change advisory board item, not a checkbox. Sequence it into the rollout plan rather than discovering it in week six.

Agentic layer: the MCP Gateway

VendorLinx AI Access Control is an MCP gateway that sits inline between AI platforms and the enterprise applications they access. It inspects every MCP tool call in real time, evaluating not just which server an agent can reach but which tools it can invoke, which actions it can take, and which data it can touch. Requests are approved in milliseconds or blocked before they cause harm, evaluated against the same access profiles used for humans and non-human identities. Every action is logged with the initiating identity, the tools called, and the outcome.

                   Access profile
                 (one policy for all)
                          │
                          ▼
   AI agent  ────────▶  Linx MCP  ────────▶  Enterprise app
(acts for a human)      gateway              (via MCP server)
                          │
                          ▼
                    Audit record
                (agent back to human)

Figure 4. Every other connector in this guide is a polling API client operating after the fact. The gateway is inline and synchronous, on the critical path of the agent's request. That changes the risk profile entirely.

OpenQuestions specific to inline enforcement:

  • Failure mode. If the gateway is unreachable, do agent tool calls fail open or fail closed? There is no universally correct answer, but there is a wrong answer for your environment, and you need to know which one you are getting.
  • Hosting. Is the gateway Linx-hosted, meaning your agent traffic and its payloads transit the vendor, or customer-hosted? This is a data flow question, not a preference.
  • Latency budget. "Milliseconds" needs a p99, not an adjective.
  • Protocol coverage. MCP transports vary. A gateway can only intercept what routes through it, and direct agent-to-API calls that bypass MCP entirely are invisible.
  • Identity binding. How is the human or NHI behind an agent session established and asserted, and can an agent spoof it?

Vendor due diligence

Grouped by what a weak answer would tell you.

OpenArchitecture integrity

  1. On-premises Active Directory: indirect through Entra Connect, or a customer-hosted collector? Do AD-only accounts with no Entra representation appear in the graph?
  2. Does the Okta connector use scoped OAuth (private_key_jwt) or a legacy SSWS token?
  3. Is workload identity federation supported for Entra, or is a certificate or secret required?
  4. Does the AWS connector enforce an ExternalId on the cross-account role?

OpenOperational reliability

  1. Baseline sync duration and rate limit consumption for an org of our size.
  2. If an event subscription lapses or a delta cursor is invalidated, is the failure alerted or does the graph silently go stale?
  3. What is the AI custom connector actually doing for an application with no API? Is the generated connector reviewable and version controlled before it runs?

OpenBlast radius

  1. Exactly which additional grants does remediation require beyond discovery, and can we run indefinitely in read-only?
  2. For JIT, is expiry native to the target platform (Entra PIM) or dependent on a Linx callback?
  3. How are break-glass and vendor-support accounts excluded from autonomous action, and who can change that exclusion list?

OpenAgentic layer

  1. Does the MCP gateway fail open or fail closed, and where is it hosted?
  2. What is the p99 added latency on a tool call?
  3. How is the human identity behind an agent session asserted, and what prevents spoofing?

OpenData governance

  1. Data residency, per-tenant key isolation, log retention.
  2. Sub-processor list, and whether customer identity data touches any model training.
